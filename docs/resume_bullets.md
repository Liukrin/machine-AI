# 项目简历条目 · 机械设备运维知识问答 RAG 平台

> 所有数字均取自仓库既有文件，逐条标注出处；无依据的表述见「四、缺依据清单」。

## 一、项目一句话定位

维修工翻 4 份手册（179 页）找答案费劲，本系统给带出处回答，答不出就明说、不编。

## 二、简历正文条目（4 条）

1. 独立搭建 4 份手册的 S1–S5 五阶段端到端管线，后端 FastAPI、前端 React 全栈。（出处：README.md）

2. 对比纯向量与混合检索后选定混合，总体 R@1 0.583→0.778、MRR@10 0.720→0.836。（出处：eval/reports/s3_summary.md）

3. 用 LangGraph 编排检索→生成→校验，加基于向量距离标定的拒答闸与引用校验，知识库外问题被显式拒答。（出处：src/s4_agent/graph.py、configs/config.yaml）

4. 构建 36 题评测集按 text/table/hard 分组评测，定位「纯编号查询」三路检索均未命中的盲区。（出处：eval/reports/s3_summary.md）

## 三、面试追问预案（6 组）

Q：为什么不直接用向量检索，混合检索到底提升了什么？
A：纯向量基线总体 R@1 只有 0.583，能靠语义召回但漏掉表头、编号等字面匹配；混合 BM25 后总体 R@1 提到 0.778，table 的 R@1 从 0.143 提到 0.429，字面匹配补上了「问题→精确片段」的信号。（出处：eval/reports/s3_summary.md）

Q：为什么评测后放弃了 rerank？
A：rerank 把 hard 组 R@10 从 0.60 提到 0.80，但总体 R@1 从 0.778 跌到 0.639，7 条正文题被降权，单题还多耗 3.07 秒；语料 text 占 29/36，全局精排净亏，于是做了对比后否决。（出处：eval/reports/s3_summary.md）

Q：拒答阈值怎么定的，有没有失效案例？
A：取 36 条正样本向量距离的 P95=0.3567 作阈值，超过就拒答；但负样本「挖掘机液压泵」距离 0.3347 小于阈值会穿过，说明语义邻近查询单靠一个距离闸挡不住，只能如实记录。（出处：configs/config.yaml、docs/process_log.md）

Q：怎么防止 LLM 幻觉？
A：不指望 LLM 自律，它一定会编，所以只做外部确定性校验：答案句子的 bigram 重合率低于 0.15 就标可疑；引用的 chunk_id 必须落在检索结果白名单内，否则标为虚构引用。但校验只能标出可疑，不能保证百分百拦住。（出处：src/s4_agent/verify.py）

Q：评测集 36 题怎么来的，会不会太少？
A：从手册 chunk 分层抽样 text 30 / table 10，人工核对删掉 4 条重复题，最终 36 题分 text 29/table 7、easy 14/medium 17/hard 5。会偏少——hard 仅 5 题、table 仅 7 题，小分组指标方差大，只能做相对对比。（出处：eval/reports/s3_summary.md）

Q：这个项目最大的局限是什么？
A：数字密集表格是检索盲区：「泵轴对应部件编号」这类查询，基线/混合/rerank 三路都在 top-10 之外，向量和 BM25 都覆盖不了「编号→内容」；且全链路未上线，所有指标都来自离线评测。（出处：eval/reports/s3_summary.md）

## 四、缺依据清单

- 端到端响应延迟：api.py 的 elapsed_ms 是运行时逐次打印，仓库里没有固定的评测均值，故正文未写延迟数字。
- 引用校验器自身的量化效果（准确率/误报率）：verify.py 只有 bigram 阈值 0.15 与 chunk_id 白名单逻辑，没有对校验器本身的评测数字。
- 拒答闸的准确率/召回率：config.yaml 只给了阈值标定（P95 0.3567、负样本 0.3347），没有「拒答正确率」这类汇总指标。
- 上线后效果（真实查询量、用户反馈、延迟分布）：项目为开发环境，无生产数据。
- 体验类/主观类结论（如「提升用户体验」「大幅优化」）：仓库无数据支撑，全文未写。
