# 已知缺陷与边界（bad case 分析）

本文档整理开发过程中定位过的失败案例，记录已知缺陷与系统边界，不是待办清单。已修复或处置：切句 bug、SSE 行尾、gold 跨块、全局 rerank；未修复的结构性局限：数字密集表检索、拒答阈值重叠；未清理（如实记录）：知识库混入自造样例数据。

## 案例

### 1. 数字密集表格检索失败（qa_038）

| 字段 | 内容 |
|---|---|
| 现象 | 评测题 qa_038「泵轴对应的部件编号是多少？」（gold=4_c0310）在纯向量、混合、混合+rerank 三路均未命中 top-10；向量侧实际 top-3 距离 0.2759/0.2877/0.2887，均非 gold |
| 定位过程 | 该题 gold 是数字密集的零件编号表；比对问题与表格文本，发现「部件编号」与表内编号串既无语义共现、也无字面重叠 |
| 根因 | 纯编号/零件表是 embedding（语义）与 BM25（字面）的共同盲区，两者都缺「编号→内容」的字段级映射能力 |
| 处置 | 未修复，原因是需表格结构化解析或字段级索引，超出当前检索方案，如实记录为结构性局限 |
| 残留风险 | 同类「型号/编号→参数」查询会持续漏召回 |

> 出处：eval/reports/s3_summary.md、eval/reports/s3_baseline.md

### 2. 拒答阈值正负样本重叠

| 字段 | 内容 |
|---|---|
| 现象 | 负样本「挖掘机液压泵」的向量 distance 0.3347 小于正样本 P95=0.3567，穿过拒答闸 |
| 定位过程 | 用 36 条正样本标定距离 P95、6 条负样本测 min，发现正负样本无清晰间隔（0.3347 < 0.3567） |
| 根因 | 语义邻近查询与正样本在向量空间天然接近，单一标量距离无法切开两者 |
| 处置 | 未修复，原因是单一距离闸固有局限；按正样本 P95 取 τ=0.3567 并如实记录重叠 |
| 残留风险 | 语义相邻的库外问题可能被当作可答而漏拒 |

> 出处：configs/config.yaml、docs/process_log.md

### 3. 全局 rerank 导致总体 R@1 下降

| 字段 | 内容 |
|---|---|
| 现象 | 混合检索后接 CrossEncoder 精排，总体 R@1 从 0.778 跌到 0.639（−0.139）、MRR@10 0.836→0.765 |
| 定位过程 | 分组看，hard R@10 0.60→0.80、table R@10 0.714→0.857 是提升的，但 7 条混合已排第 1 的正文题被降权到 2~8 位，单题还多耗 3.07s（36 题 110.7s） |
| 根因 | 全局精排一刀切地做「语义重排」，对占 29/36 的 text 题只带来排序扰动，收益集中在 hard/table 少数题 |
| 处置 | 已修复（弃用）；config s3_rerank.enabled=false，脚本保留可复现 |
| 残留风险 | hard/table 的召回上限未再提升，选择性 rerank 未实现 |

> 出处：eval/reports/s3_summary.md、configs/config.yaml

### 4. 评测集 gold 答案跨 chunk

| 字段 | 内容 |
|---|---|
| 现象 | qa_001「同心度允差」的答案实际落在相邻 chunk 1_c0030（「不同心度允差0.1mm」），而非原标 gold 1_c0029（「校正水平不平度<0.1mm」） |
| 定位过程 | 人工核对答案时发现语义答案在相邻块；回查发现是 chunk 重叠 + heading 分组把同一答案点切进了两个相邻 chunk |
| 根因 | 切分重叠与 heading 分组使一个答案点同时出现在相邻块，只标单一 gold 会误伤正确召回 |
| 处置 | 已修复；qa_001 的 gold 改为 1_c0030，原 1_c0029 记入 gold_alt 兜底 |
| 残留风险 | 其他题可能仍有隐藏跨块答案，gold_alt 依赖人工发现，未自动生成邻居 alt |

> 出处：docs/process_log.md、eval/reports/s3_summary.md

### 5. 引用校验器切句 bug

| 字段 | 内容 |
|---|---|
| 现象 | LLM 把引用标在句末标点之后（如「…0.05mm。[2_c0016]」），按「。！？」切句时 [2_c0016] 被切到下一碎片，主句被误判「无引用」 |
| 定位过程 | 校验结果出现大量「无引用句」误报，逐句比对发现引用标记位置在句号之后 |
| 根因 | 切句发生在引用搬移之前，引用标记与主句被句末标点拆开 |
| 处置 | 已修复；切句前先把紧跟句末标点后的 [chunk_id] 移到标点之前（_move_citations_before_punct） |
| 残留风险 | 仅处理了「句末标点后紧跟引用」一种位置，其他非常规位置仍可能误判 |

> 出处：docs/process_log.md、src/s4_agent/verify.py

### 6. SSE 行尾 CRLF 不兼容

| 字段 | 内容 |
|---|---|
| 现象 | 前端按 \n\n 切分 SSE 事件，但后端 sse-starlette 用 \r\n 行尾，CRLF 流里没有 \n\n，事件积压到流末一次性派发，只渲染出残缺 done 行、拒答路径崩溃 |
| 定位过程 | 前端只出现「done」事件而 retrieval/token/verification 全丢，回查原始字节发现行尾是 \r\n 而非 \n |
| 根因 | SSE 规范允许 \r\n、\n、\r 三种行尾，实现时硬编码了 \n\n |
| 处置 | 已修复；改用 /\r?\n\r?\n/ 兼容三种行尾切分事件 |
| 残留风险 | 无（已兼容全部行尾），但提示接入第三方 SSE 源仍需按规范处理 |

> 出处：docs/process_log.md

### 7. 知识库混入自造样例数据

| 字段 | 内容 |
|---|---|
| 现象 | chunks.jsonl 与 Chroma（equipment_manual）均为 457 条，其中 18 条 doc_id 为 sample_* 的自造样例，可被检索与引用 |
| 定位过程 | 按 doc_id 统计分布，发现 sample_cooler_manual 9 / sample_pump_manual 5 / sample_valve_manual 4，且 Chroma 中 id 前缀分布与 chunks.jsonl 完全一致 |

## 已知结构性局限

1. **数字密集表格检索（qa_038）**：文本 embedding 与 BM25 分别是「语义匹配」和「字面匹配」，都没有「编号→内容」的字段级结构概念，对纯编号/零件表查询在原理上就难以命中；除非对表格做结构化解析成键值对或建字段级倒排索引，否则当前方案解决不了。

2. **拒答阈值正负样本重叠**：语义邻近的库外查询在向量空间天然落在正样本区间（负样本 0.3347 < 正样本 P95 0.3567），单一标量距离无法切开两者；当前只能取正样本 P95 并接受误拒/漏拒的重叠，多级阈值或显著扩大负样本集才有改善空间，未实现。

3. **全局 rerank 的取舍困局**：rerank 对 hard/table 有益（R@10 0.60→0.80、0.714→0.857）却对 text/easy 有害（总体 R@1 0.778→0.639），全局一刀切净亏；要「按类型/难度选择性精排」需要额外的路由与评测闭环，当前方案未实现。
