# 已知缺陷与边界（bad case 分析）

本文档整理开发过程中定位过的失败案例，记录已知缺陷与系统边界，不是待办清单。已修复或处置：切句 bug、SSE 行尾、gold 跨块、全局 rerank；未修复的结构性局限：数字密集表检索、拒答阈值重叠、引用校验对数值不敏感；未清理（如实记录）：知识库混入自造样例数据；性能评测观察（如实记录）：拒答闸误拒库内有效问题（阈值在同一批题上标定的必然结果）、单题上下文 token 膨胀；答案级评测发现（未修复）：拒答闸在新题上误拒、追问被拦截、张冠李戴、故障表与 D 型手册检索不到。

## 案例

### 1. 数字密集表格检索失败（qa_038）

| 字段 | 内容 |
|---|---|
| 现象 | 评测题 qa_038「泵轴对应的部件编号是多少？」（gold=4_c0310）在纯向量、混合、混合+rerank 三路均未命中 top-10；向量侧实际 top-3 距离 0.2759/0.2877/0.2887，均非 gold |
| 定位过程 | 该题 gold 是数字密集的零件编号表；比对问题与表格文本，发现「部件编号」与表内编号串既无语义共现、也无字面重叠 |
| 根因 | 纯编号/零件表是 embedding（语义）与 BM25（字面）的共同盲区，两者都缺「编号→内容」的字段级映射能力 |
| 处置 | 未修复，原因是需表格结构化解析或字段级索引，超出当前检索方案，如实记录为结构性局限 |
| 残留风险 | 同类「型号/编号→参数」查询会持续漏召回 |

> 出处：eval/reports/s3_summary.md、eval/reports/s3_baseline.md

### 2. 拒答阈值正负样本重叠

| 字段 | 内容 |
|---|---|
| 现象 | 负样本「挖掘机液压泵」的向量 distance 0.3347 小于正样本 P95=0.3567，穿过拒答闸 |
| 定位过程 | 用 36 条正样本标定距离 P95、6 条负样本测 min，发现正负样本无清晰间隔（0.3347 < 0.3567） |
| 根因 | 语义邻近查询与正样本在向量空间天然接近，单一标量距离无法切开两者 |
| 处置 | 未修复，原因是单一距离闸固有局限；按正样本 P95 取 τ=0.3567 并如实记录重叠 |
| 残留风险 | 语义相邻的库外问题可能被当作可答而漏拒 |

> 出处：configs/config.yaml、docs/process_log.md

### 3. 全局 rerank 导致总体 R@1 下降

| 字段 | 内容 |
|---|---|
| 现象 | 混合检索后接 CrossEncoder 精排，总体 R@1 从 0.778 跌到 0.639（−0.139）、MRR@10 0.836→0.765 |
| 定位过程 | 分组看，hard R@10 0.60→0.80、table R@10 0.714→0.857 是提升的，但 7 条混合已排第 1 的正文题被降权到 2~8 位，单题还多耗 3.07s（36 题 110.7s） |
| 根因 | 全局精排一刀切地做「语义重排」，对占 29/36 的 text 题只带来排序扰动，收益集中在 hard/table 少数题 |
| 处置 | 已修复（弃用）；config s3_rerank.enabled=false，脚本保留可复现 |
| 残留风险 | hard/table 的召回上限未再提升，选择性 rerank 未实现 |

> 出处：eval/reports/s3_summary.md、configs/config.yaml

### 4. 评测集 gold 答案跨 chunk

| 字段 | 内容 |
|---|---|
| 现象 | qa_001「同心度允差」的答案实际落在相邻 chunk 1_c0030（「不同心度允差0.1mm」），而非原标 gold 1_c0029（「校正水平不平度<0.1mm」） |
| 定位过程 | 人工核对答案时发现语义答案在相邻块；回查发现是 chunk 重叠 + heading 分组把同一答案点切进了两个相邻 chunk |
| 根因 | 切分重叠与 heading 分组使一个答案点同时出现在相邻块，只标单一 gold 会误伤正确召回 |
| 处置 | 已修复；qa_001 的 gold 改为 1_c0030，原 1_c0029 记入 gold_alt 兜底 |
| 残留风险 | 其他题可能仍有隐藏跨块答案，gold_alt 依赖人工发现，未自动生成邻居 alt |

> 出处：docs/process_log.md、eval/reports/s3_summary.md

### 5. 引用校验器切句 bug

| 字段 | 内容 |
|---|---|
| 现象 | LLM 把引用标在句末标点之后（如「…0.05mm。[2_c0016]」），按「。！？」切句时 [2_c0016] 被切到下一碎片，主句被误判「无引用」 |
| 定位过程 | 校验结果出现大量「无引用句」误报，逐句比对发现引用标记位置在句号之后 |
| 根因 | 切句发生在引用搬移之前，引用标记与主句被句末标点拆开 |
| 处置 | 已修复；切句前先把紧跟句末标点后的 [chunk_id] 移到标点之前（_move_citations_before_punct） |
| 残留风险 | 仅处理了「句末标点后紧跟引用」一种位置，其他非常规位置仍可能误判 |

> 出处：docs/process_log.md、src/s4_agent/verify.py

### 6. SSE 行尾 CRLF 不兼容

| 字段 | 内容 |
|---|---|
| 现象 | 前端按 \n\n 切分 SSE 事件，但后端 sse-starlette 用 \r\n 行尾，CRLF 流里没有 \n\n，事件积压到流末一次性派发，只渲染出残缺 done 行、拒答路径崩溃 |
| 定位过程 | 前端只出现「done」事件而 retrieval/token/verification 全丢，回查原始字节发现行尾是 \r\n 而非 \n |
| 根因 | SSE 规范允许 \r\n、\n、\r 三种行尾，实现时硬编码了 \n\n |
| 处置 | 已修复；改用 /\r?\n\r?\n/ 兼容三种行尾切分事件 |
| 残留风险 | 无（已兼容全部行尾），但提示接入第三方 SSE 源仍需按规范处理 |

> 出处：docs/process_log.md

### 7. 知识库混入自造样例数据

### 8. 拒答闸误拒库内有效问题（P95 阈值的固有代价）

| 字段 | 内容 |
|---|---|
| 现象 | s5_perf 实测中 qa_002、qa_018 两道评测集金标题的 vector top-1 distance 为 0.3892 / 0.3724，均超过 τ=0.3567 被拒答，误拒率 2/36 = 5.6% |
| 定位过程 | 性能评测按题打印 distance 与 τ 对比时发现；两题均在 qa_set 内、gold chunk 存在于知识库 |
| 根因 | τ 就是在这 36 题的 distance 上取的 P95（线性插值），同一批题里必然恰有 2 题高于阈值；所以 2/36 = 5.6% 是阈值定义的直接结果，不是在独立测试集上测得的误拒率 |
| 处置 | 未调整。误拒与漏拒是同一阈值的两端：降低 τ 会同时放大漏拒（案例 2 已记录负样本 0.3347 穿闸），单一标量阈值无法同时改善两端。本项目选择容忍误拒，以换取对库外问题的拦截——这是取舍不是缺陷 |
| 残留风险 | 约 5% 的库内有效提问会收到「知识库无相关内容」 |

> 出处：eval/reports/s5_perf.md

### 9. 单题上下文 token 异常膨胀（qa_031）

| 字段 | 内容 |
|---|---|
| 现象 | s5_perf 首测 qa_031 单题 input 10118 tokens，其余题 ≤ 1148，约 10 倍（换 C 组提示词后复测为 10122） |
| 定位过程 | 重跑该题检索并逐个打印 5 个候选：全部为 table 类型——1_c0018（1538 字符）、1_c0024（gold，4847）、1_c0023（4732）、1_c0016（1789）、1_c0022（4425），build_search_text 合计 17331 字符；膨胀源是 3 张 4400+ 字符的大表全单元格拼接，而非某个单点异常 |
| 根因 | table chunk 的检索文本按「表头 + 全部单元格拼接」构造，大表整表拼接后上下文随之膨胀；答案行可能落在大表任意行，不带整表就无法保证可答 |
| 处置 | 未截断。截断表行可能截掉答案行，属表格可答性与 token 成本的取舍，如实记录 |
| 残留风险 | 命中大表的问题单题 input 可达万级 token，耗时与成本随上下文线性上升（首测该题 t_total 2154ms 尚在正常区间，主要代价在 token 而非延迟） |

> 出处：eval/reports/s5_perf.md

### 10. 引用校验对数值错误不敏感

| 字段 | 内容 |
|---|---|
| 现象 | 以 1_c0030（原文「不同心度允差0.1毫米」）为依据构造两句答案：「…允差为0.1毫米。[1_c0030]」与「…允差为5毫米。[1_c0030]」，verify_citation 均返回 suspicious 0、fabricated_ids 为空，数字写错没有被标出 |
| 定位过程 | 用正确答案与改错数字的答案做探针，逐一比对校验输出 |
| 根因 | 可疑句判定只取句中汉字的二元组，数字和单位不参与比对；而且对照的是本轮全部检索片段拼起来的文本，而不是句子所引用的那个片段；改错数字不改变汉字二元组，重合度照样过线 |
| 处置 | 未修复，如实记录。改进方向：用确定性代码核对答案里的数值与单位是否出现在所引片段中 |
| 残留风险 | 维修场景的关键信息多是数值（允差、扭矩、压力），数值错误会以「引用有效、无可疑句」的状态展示给用户 |

> 出处：src/s4_agent/verify.py

### 11. 拒答闸在新题上误拒：证据已检索到却不作答

| 字段 | 内容 |
|---|---|
| 现象 | 证据已全部召回、却被拒答闸拦掉的应答题，dev 6 道、test 10 道。只看单轮问题，被闸误拒的是 dev 4/57、test 5/54，例如「Wilo-WR 更换填料的操作步骤是什么？」（距离 0.3636）、「Model 3700 的年度检查包括哪些项目？」（0.3790）、「Wilo-WR 的零件清单里，零件号 458 是什么零件？」（0.3928） |
| 定位过程 | 答案级评测按「证据是否召回 × 是否作答」分解失分：证据召回且作答的题全部答对（dev 49/49、test 43/43），失分集中在「证据召回了但没作答」这一格 |
| 根因 | τ=0.3567 是在旧评测集 36 题上取的 P95，没有在另一批题上验证过；9 道被误拒的单轮题里有 8 道的距离落在 0.36–0.40，紧贴阈值。拒答闸只看向量 top-1 距离，不看 BM25 是否命中、也不看融合后的排序 |
| 处置 | 未修复，如实记录。τ 不在这批题上重调（dev 留给后续重做拒答闸时标定，test 只报数） |
| 残留风险 | 大约每 12 个正常的单轮提问就有 1 个被直接拒答（两个划分合计 9/111） |

### 12. 追问被拒答闸拦截

| 字段 | 内容 |
|---|---|
| 现象 | 10 道多轮追问（「MX 组呢？」「那带油嘴的呢？」「如果是一直亮着不闪呢？」）全部被拒答闸拦截，距离 0.38–0.54 |
| 定位过程 | 评测集里每道追问都附了改写成独立问题的版本；按线上现状只发最后一句时 0/10 答对，改写后 7/10 答对（dev 4/5、test 3/5） |
| 根因 | 后端只接收当前这一句，问句脱离上文后语义不完整，和任何片段的向量距离都大 |
| 处置 | 未修复。前端的对话历史只用于展示 |
| 残留风险 | 界面是对话形态，用户自然会追问，得到的却是「手册中没有找到与该问题相关的内容」 |

### 13. 张冠李戴：用别的设备或别的手册的内容作答

| 字段 | 内容 |
|---|---|
| 现象 | test「减速机齿轮箱的润滑油多久更换一次？」（语料里没有减速机）→ 答「更换润滑油最少每 3 个月（2000 运行小时）更换一次 [4_c0182]」，用的是 Model 3700 泵手册；dev「D型泵要停很久不用，里面的水用不用放掉？」→ 答案引用的全是 Wilo-WR 手册的片段（2_c0040、2_c0002） |
| 定位过程 | 前者出现在「应拒答却作答」清单里（29 道应拒答题中唯一漏掉的一道）；后者由「串手册」指标发现（引用的片段没有一个出自题目问的那份手册） |
| 根因 | 检索不区分手册和设备；提示词只要求依据检索内容作答，没有要求核对检索内容讲的是不是被问到的对象。这两个答案的每句话相对检索片段都「有依据」，引用校验显示通过，忠实度评审也判为有依据 |
| 处置 | 未修复。评测里单列了「串手册」指标 |
| 残留风险 | 这类答案带着引用、校验通过，是用户最难察觉的一种错误；维修场景里不同型号的参数不能混用 |

### 14. 检索不到证据：D 型手册与故障表

| 字段 | 内容 |
|---|---|
| 现象 | 模型自述「检索内容不足」的 5 道应答题（dev 1、test 4），证据都没进前 5：D 型泵 3 道（盘车要求、停泵顺序、振动原因）、Wilo-WR 故障表 1 道、Model 3700 故障排除表 1 道。test 上 D 型手册的题完全答对 5/9，是四份手册里最低的 |
| 定位过程 | 逐题看证据片段在两路检索里的排名：「D型多级离心泵停止运转时应按什么顺序操作？」的证据 1_c0031，向量排第 39、BM25 排第 16；「按 Model 3700 的故障排除表，轴承运转过热…」的证据 4_c0327，向量排第 42、BM25 排第 8 |
| 根因 | D 型手册的片段文本只带章节名（「十四、起动、停止和运行」），不带手册名，问句里的「D型泵」帮不上忙，前 5 常被别的手册占满。4_c0327 这张故障排除表有 939 个 token，超过 embedding 模型的 512 上限，后半张表没有进入向量 |
| 处置 | 未修复。检索没找到证据时，模型多数会如实说资料不足而不是借用别的手册，这一点是好的 |
| 残留风险 | 故障排查是维修人员最常问的一类问题，而这 5 道题里有 3 道问的正是故障表（D 型泵振动、Wilo-WR 电机过载、Model 3700 轴承过热） |

## 已知结构性局限

1. **数字密集表格检索（qa_038）**：文本 embedding 与 BM25 分别是「语义匹配」和「字面匹配」，都没有「编号→内容」的字段级结构概念，对纯编号/零件表查询在原理上就难以命中；除非对表格做结构化解析成键值对或建字段级倒排索引，否则当前方案解决不了。

2. **拒答阈值正负样本重叠**：语义邻近的库外查询在向量空间天然落在正样本区间（负样本 0.3347 < 正样本 P95 0.3567），单一标量距离无法切开两者；当前只能取正样本 P95 并接受误拒/漏拒的重叠，多级阈值或显著扩大负样本集才有改善空间，未实现。

3. **全局 rerank 的取舍困局**：rerank 对 hard/table 有益（R@10 0.60→0.80、0.714→0.857）却对 text/easy 有害（总体 R@1 0.778→0.639），全局一刀切净亏；要「按类型/难度选择性精排」需要额外的路由与评测闭环，当前方案未实现。
