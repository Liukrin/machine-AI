# 工具调用 Agent：设计与评测

阶段 2（改造路线第 5 条）把问答从「检索一次 → 生成」的固定流水线，改成 LangGraph 编排的工具调用 Agent，
线上 `/api/ask` 直接执行这张图并流式输出。旧流水线保留为 `rag` 模式，作为对照基线。

本文的数字都来自 `eval/answer_eval/` 下的评测产物，生成命令见文末。

## 1. 为什么改：基线的失分在哪

阶段 1 的答案级评测（`docs/answer_eval.md`）给出了很清楚的信号：**只要证据检索到并且作答了，基线就全部答对**
（dev 49/49、test 43/43），失分都出在生成之前：

| 失分来源（基线，dev + test 合计，各类有重叠） | 题数 | Agent 里对应的改法 |
|---|---|---|
| 拒答闸误拒（向量距离超过 τ 就不调模型），且证据其实已检索到 | 16（dev 6 / test 10） | 去掉硬闸，距离只作「相关度低」提示；查不到时由模型说明 |
| 多轮追问：只发最后一句，全被拒答 | 10（dev 5 / test 5） | 前端传对话历史，模型结合上文改写后再检索 |
| 证据没检索全（D 型手册片段不带手册名、大表格向量被截断等） | 13（dev 7 / test 6） | 模型可换说法、限定手册重搜；表格按行查（`lookup_table`） |
| 串手册 / 串设备 | 2（dev 1 道应答题引用了别的手册；test 1 道库外题拿泵手册作答） | 系统提示词给出手册清单，要求按设备选手册、问到清单外的设备直接说明 |

另外，基线不会做「查到之后再加工」的事：换算单位要靠模型心算，判断实测值是否超限也由模型自己比大小，
后者违反 CLAUDE.md 第 3 条（物理阈值判决由确定性 Python 执行）。为此新增了 Agent 多步任务集（第 5 节）。

## 2. 图结构

```
 question ─┐
 history ──┤
           ▼
   ┌───────────────┐   系统先用原问题检索一次（有历史时拼上上一轮的问题），
   │   presearch   │   结果以一次 search_manuals 调用的形式放进对话
   └───────┬───────┘
           ▼
   ┌───────────────┐   有工具调用且未到上限    ┌───────────────┐
   │     agent     │ ───────────────────────▶ │     tools     │  每个工具有超时；
   │ (模型 + 工具)  │ ◀─────────────────────── │               │  出错作为观察结果回给模型
   └───────┬───────┘                          └───────────────┘
           │ 直接作答，或到达轮数上限后以 tool_choice=none 强制作答
           ▼
   ┌───────────────┐
   │   finalize    │   引用校验（引用的 chunk_id 是否都在本次工具返回过的片段里）、拒答判定
   └───────────────┘
```

代码：`src/s4_agent/agent.py`（图与节点）、`tools.py`（工具）、`units.py`（换算与限值比较）、`tables.py`（表格按行入库）。
命令行试问：`python src/s4_agent/agent.py "问题"`。

## 3. 五个工具

| 工具 | 做什么 | 针对的问题 | 确定性保证 |
|---|---|---|---|
| `search_manuals(query, manual?, kind?)` | BM25 + 向量混合检索（RRF），可限定手册、只搜正文或表格 | 检索没召回、串手册 | 不加过滤时与 rag 模式的检索逐题一致（181/181 题核对过）；返回结果标注向量距离，超过 τ 时提示「相关度低」 |
| `lookup_table(keywords, manual?)` | 在表格行里按关键词查，返回命中的行和表头 | 零件编号、故障表、扭矩表（关键词短，整表 900+ token 时检索排不上来） | HTML 表格展开成规整的行（rowspan 向下填充），存进内存 SQLite 参数化查询；≤6 行的小表整表返回；多张表里重复的行只列一次 |
| `read_section(chunk_id, before, after)` | 读同一本手册里前后相邻的片段 | 答案被切到两个片段里 | 只能读本次对话里出现过的片段 |
| `convert_unit(value, from, to, is_difference?)` | 单位换算 | 模型心算出错 | 换算系数取定义值（1 in = 25.4 mm、1 lb = 0.45359237 kg、g = 9.80665 m/s² 等），温度区分绝对值与温差 |
| `check_value(value, unit, source_chunk_id, limit_min?, limit_max?, limit_unit?)` | 实测值或设定值是否在手册规定范围内 | 物理阈值判决交给了模型 | 结论由代码比较得出；限值必须出自本次检索到的片段，且限值数字要能在该片段原文里找到，否则报错让模型重查；单位不同先换算再比较 |

工具参数用 pydantic 定义并校验，参数不合法、手册编号认不出、片段不存在、单位不认识，都以「工具调用失败：原因」的
文本回给模型，由模型修正后重试，不中断回答。

## 4. Harness 约束与工程细节

| 约束 | 取值（`configs/config.yaml` 的 `agent` 段） | 说明 |
|---|---|---|
| 工具轮数上限 | 3 | 之后以 `tool_choice=none` 强制作答，所以每题最多 4 次模型调用 |
| 单轮工具调用数上限 | 4 | 模型可以一轮并行调多个工具；多出的不执行，作为错误回给模型 |
| 单个工具超时 | 10 秒 | 超时作为错误回给模型 |
| 对话历史 | 最近 3 轮，每条回答去掉引用标记后最多 600 字 | 去引用是为了不让模型把上一轮的片段当成本轮依据来引用 |
| 生成上限 | 每次模型调用 1024 token | 与 rag 模式相同 |

几个取舍：

1. **第一次检索由代码做，而不是让模型决定**。第一次查询几乎总是用户原话，交给模型决定要多花一次模型调用（实测单次约 1–2 秒）。
   dev 上 87% 的题（67/77）看完预检索结果就直接作答，只调一次模型。
2. **去掉向量距离硬闸**。阶段 1 的闸在 τ=0.3567 上拦下了 16 道证据其实已检索到的题，追问更是全拦。
   现在距离仍然算、仍然告诉模型（「相关度低，请核实或换个说法再查」），但不再替模型做决定。
   代价是库外题要靠模型自己拒答，见第 5 节的拒答召回。
3. **限值核对的结论由代码给出**。模型负责从手册里找到限值并把参数交给 `check_value`，「是否超限」由 `units.compare` 比较得出，
   返回文本里写明「请按上面的核对结论回答，不要自行重新比较」。限值数字必须在所引片段原文里找得到，防止模型编一个限值来比。
4. **表格以行为单位给模型看**。检索结果里的表格也按行展开（「GG | GGG」「25 | 40」），比拍平的单元格好读；
   超过 2000 字的大表截断并提示改用 `lookup_table`。
5. **流式输出**。API 用 `graph.stream(stream_mode=["messages", "custom", "values"])` 同时订阅模型逐 token 输出、
   工具步骤事件（节点里用 `get_stream_writer` 发出）和最终状态。token 带 `round`（第几次模型调用）；
   某次调用最后决定调工具时，它之前流出的说明文字会再以 `thought` 事件发出，前端把它从回答区挪到步骤时间线。
6. **成本与可复现**。每次回答在 `done` 事件里给出模型调用次数、token（含缓存命中）、按单价估算的费用和接口返回的模型名。

### SSE 事件（agent 模式）

| 事件 | 内容 |
|---|---|
| `step` | `llm_start`（第几次模型调用、是否强制作答）/ `tool_start` / `tool_end`（工具名、参数、成败、摘要、耗时；换算与核对带输出原文）/ `thought` / `forced_final` |
| `retrieval` | 截至目前给模型看过的全部来源片段（累计列表，前端直接替换） |
| `token` | `{text, round}` |
| `verification` | 引用校验结果，另有 `refused`（含拒答话术且没有引用任何片段） |
| `done` | token、缓存命中 token、耗时、`finish_reason`、模型调用次数、工具调用次数、是否强制作答、模型名、估算费用、最终答案 |

请求体：`{question, history?: [{role, content}], mode?: "agent" | "rag"}`。前端在输入框下方可切换模式。

## 5. 评测

### 5.1 评测集与纪律

- **主评测集** `eval/answer_set.yaml`：阶段 1 建立的 150 题（dev 77 / test 73），本阶段没有改动。
- **Agent 多步任务集** `eval/agent_tasks.yaml`：31 题（dev 17 / test 14），单位换算 8、限值核对 8、表格精确查询 7、
  多步/跨手册 5，外加 3 道「手册没写的参数」（应说明查不到，不得编一个限值来比）；69 条关键事实，其中 44 条数值事实。
  换算结果写成「推算数值事实」：`calc` 字段给出独立写出的算式（换算系数在评测集里另写一遍，不依赖 Agent 的换算工具），
  `validate.py` 核对每个期望数字都是算式结果的正确舍入。
- 任务集在动 Agent 代码之前写好，并先用**未改动的**阶段 1 系统（系统指纹 `75198a4ed85b`）生成了基线答案，
  所以两个系统在任务集上的对比同样是「同一份题、同一套评分」。
- Agent 写完后在 dev 上跑一次。dev 上只修了评测脚本自己的问题（第 6 节第 4、5 条），没有改被测系统；
  定稿后 test 只跑一次（Agent 系统指纹 `a62c1e9b641a`）。

### 5.5 读这组数字

1. **提升来自三处，和第 1 节的失分一一对应**：去掉距离闸后误拒归零（主集 dev 10→0、test 14→0）；追问带上历史后
   多轮 10 题全部答对；换算和核对交给确定性工具后，任务集数值事实全部答对（基线 dev 17/23、test 12/21）。
   主集 test 上完全答对的区间 [0.91, 1.00] 与基线的 [0.60, 0.83] 不重叠。题量仍然小，单次运行。
2. **生成没有变得更「敢说」**：忠实度·严格略降（主集 dev 1.000→0.931，test 0.973→0.946），因为答案更长、句子更多；
   主集里评审判为无依据的 6 句（任务集另有 1 句）都是说明性的话（「以上依据……故障表」「运转中的其他检查（第 54 页）」
   「原文写作……即 2 m³/h」），不是编造的参数。数字可溯源率在两个集上都不低于 0.97。
3. **无引用句占比明显上升**（dev 0.059→0.354，test 0.014→0.373）：dev 91 句里 56 句、test 85 句里 51 句是 Markdown 表格的行
   （表格只在引言或结尾标一次出处），其余多是列表项（引用标在小标题或最后一项）。这是「逐句标注」口径和表格、列表
   排版的冲突，也确实意味着引用粒度变粗了；要按行标注还是按块标注，放到下一步的校验器（第 8 条）里定。
4. **拒答召回按规则下降，但实际行为没有变差**：Agent 被记为「作答」的 4 道应拒答题（主集 dev 2、test 1，任务集 dev 1）
   回答都以「知识库无相关内容」开头，说明查过什么，例如「检索到的泄漏量数值分别出自 Wilo-WR 手册……不能作为 D 型泵的依据」；
   只是违反提示词带上了所查片段的编号，按阶段 1 定的规则（拒答话术且不带引用才算拒答）记为作答，评审模型也把它们判为
   「给出了实质内容」。规则没有在看到结果后修改。对照：基线在 test 上漏拒的 `oos_adj_04`（减速机换油）是真的拿泵手册的
   换油周期作答，任务集 dev 的 `rf_02` 也是直接给出 Wilo-WR 的泄漏量。
5. **代价**：单题输入 token 主集约为基线的 3.5 倍、任务集约 5.6 倍；成本（输入全按未命中计）主集 4.5–5.0 倍、任务集约 6.3 倍。
   实际约六到七成输入命中缓存，按命中计主集约 0.0042–0.0043 元/题。
   主集上两次评测的耗时互有高低（dev 上 Agent 慢、test 上持平），两次运行时段不同，接口耗时本身波动大，看不出稳定差异；
   任务集上 Agent 平均 1.9 次模型调用，P50 约 4.1 秒，比基线慢 1.7–1.8 秒，这是确定的代价。
6. **评测本身的局限**：两个评测集都由 Claude 编写、只经过脚本校验，尚未人工复核；任务集针对的正是 Agent 新增的能力，
   基线在上面吃亏是设计使然，它衡量的是「新能力是否可靠」，不是两个系统的综合优劣。评审模型与生成模型相同，
   人工校准（`calibrate.py`）还没做。

## 6. 开发中发现的问题

详细记录见 `docs/process_log.md` 第 14–19 条，这里列要点：

1. **模型别名已经变了**：工具调用探测时发现接口返回的 `model` 字段是 `deepseek-flash`。DeepSeek 文档显示 `deepseek-chat` 是旧别名
   （2026-04-24 公告三个月后停用，目前仍可调用），现在由 V4.1-Flash 的非思考模式提供服务。本阶段两套系统用同一个模型名，对比不受影响；
   Agent 模式的 `done` 事件和评测记录已保存接口返回的模型名。评测之后已改用 `deepseek-flash` 并显式关闭思考模式（process_log 第 20 条）。
2. **工具缺单位，模型换了一个错的单位**：试问「管径 200mm 时允许的力矩 Mz（表中 85 daN·m）换算成 N·m」，换算工具不认识 daN·m 而报错，
   模型改用 kgf·m 重试，答出「85 daN·m = 85 kgf·m = 833.6 N·m」（正确是 850 N·m）。工具算得没错，错在模型交给它的单位。已补齐 daN·m 等单位。
3. **限值先换算再核对被拒**：模型把手册限值 4 L/min 先换算成 0.24 m³/h 再交给 `check_value`，原文核对找不到 0.24 而报错；
   改传原文的数值和单位后通过，但多花了一轮。参数说明改成「照抄原文的数值和单位，由工具换算」。
4. **评测正则漏了正确写法**（评测脚本问题）：任务集基线 dev 上「折合每分钟约 3.33 升」被判为没答出 3.33 L/min。修正事实模式后两个系统一起重评。
5. **换算句被判引用不成立**（评测脚本问题）：Agent 按要求给换算句标原始数值所在的片段，评审只把计算输出列为依据，
   代码判引用不成立（任务集 dev 5/37）；答案把工具给的 3.333 再舍入成 3.33，又被判为数字找不到出处。
   改为由代码核对：依据是工具输出时，所标片段须是限值出处或含被换算的原始数值；带小数的数是工具精确值的正确舍入也算可溯源。
   只影响有工具输出的答案，基线分数不变（已用 `run.py --reuse` 复算核对）。
